# Trend 分布式趋势分析服务

分布式指标数据采集与分析平台，将企业各系统中海量、杂乱的原始监控数据，通过滑动窗口分位值算法压缩为高质量、可查询的趋势数据集。

**Trend 的核心价值不是"采集数据"，而是让数据可用、可信、可比。**

原始监控数据的问题在于：数据量太大无法直接消费，平均值掩盖了真实风险，瞬时值又充满噪声，跨期对比几乎不可能规模化。Trend 通过滑动窗口分位值计算，将原始数据转化为 **六个精确的分位值序列（p99/p95/p90/p70/p50/p30）**——它们天然构成趋势区间带，既不会遗漏峰值风险，也不会被瞬时毛刺干扰，是大模型进行容量分析和趋势判断的最佳数据输入。

**数据流**：

1. Master 只有 Leader 节点会按 cron 周期从 MySQL 读取任务配置，发布到 etcd 队列
2. Worker 订阅 etcd 任务队列，从数据源（Elasticsearch/MySQL）拉取原始指标数据
3. Worker 计算分位值后写入 MySQL 分表 `metric_features_00` ~ `metric_features_09`
4. 查询端通过 Master API 的 `/api/v1/trend/` 接口读取趋势数据

## 功能

- **分布式调度**：基于 Etcd Leader 选举 + gocron 定时触发，单 Leader 下发，多 Worker 并行执行
- **配置热加载**：Worker 启动时从 Master API 获取集群级配置（数据源、存储、etcd 地址），无需本地配置文件
- **分位值计算**：从 ES 拉取原始指标，计算 p99/p95/p90/p70/p50/p30
- **版本化指标属性**：`trend_cluster_task_version` 表驱动，零代码新增指标，历史数据自带版本号保证向后兼容
- **分表存储**：结果按 `calc_instance_id % 10` 路由到 `metric_features_00` ~ `metric_features_09`，含 `cluster_name` 隔离
- **背压控制**：Master 端按 Worker 负载动态调节任务分发速率
- **Prometheus 监控**：Master/Worker 各自暴露存活状态、超时任务数、任务失败数等指标
- **趋势查询 API**：Prometheus query_range 兼容格式的时序数据查询，按集群/实例/指标/分位值精确查询

## 从噪声到信号：Trend 的数据处理能力

### 问题：原始数据无法直接用于智能化分析

以一台数据库实例的 CPU 监控为例：

```
原始数据（Elasticsearch）：
  每秒 1 条记录，一天 86400 条，一个月 250W 条
  包含瞬时毛刺（GC 暂停、网络抖动）、数据空洞、噪声波动

直接给大模型？
  ✗ 数据量太大（数十万 tokens），注意力被噪声稀释
  ✗ 瞬时峰值会被当作异常，实际只是毛刺
  ✗ 平均值 35% 掩盖了每天 2 小时的 90% 高峰
  ✗ 无法做跨期对比（昨天这时候正常吗？）
```

### 解法：滑动窗口分位值

```
Trend 的处理方式：
  每 1 分钟执行一次，窗口覆盖最近 5 分钟原始数据
  计算 6 个精确分位值：p99 / p95 / p90 / p70 / p50 / p30

结果：
  每分钟产出 1 个数据点，每个点包含 6 个分位值
  12 小时 = 720 个数据点 × 6 分位 = 4320 个精确值

这组数据的特点：
  ✓ 无损：每个分位值都从原始样本直接计算，不做近似
  ✓ 无缝：相邻窗口重叠 4 分钟，任何时间点都被覆盖
  ✓ 去噪：分位值天然过滤瞬时毛刺（p99 不是 max）
  ✓ 带区间：p50-p99 构成趋势区间带，一眼看出波动范围
  ✓ 可对比：昨天的 p99 vs 今天的 p99，精确可比
```

### 数据对比

```
同一时段，三种视角的对比：

原始数据视角（ES，5min粒度，720个原始点）：
  [42.1, 38.5, 95.2*, 41.3, 39.8, 88.1*, 40.2, ...]
  ↑ 满屏噪声，两个毛刺(95.2, 88.1)淹没在数据中

平均值视角（传统监控面板）：
  "CPU 平均使用率：35%"
  ↑ 完全看不到 90% 的峰值风险

Trend 分位值视角（每分钟1个点，6分位）：
  p99: 78 → 80 → 82 → 85 → 87 → 88  （持续攀升，风险明确）
  p95: 72 → 74 → 76 → 78 → 80 → 81
  p50: 35 → 36 → 35 → 37 → 36 → 35  （基线稳定）
  p30: 18 → 19 → 18 → 19 → 18 → 18
  ↑ 趋势清晰：p99 持续上升但 p50 稳定 → 说明峰值时段在恶化
  ↑ 数据量：720×6 = 4320 个值，远低于原始数据但信息量远超平均值
```

### 滑动窗口机制

传统监控系统的常见做法是**非重叠时间桶**：将时间按固定区间切分（如每 5 分钟一个桶），每条原始数据只属于一个桶。**窗口边界处的数据被硬切割，跨越边界的异常事件会被拆散到两个桶中，导致两侧的分位值都被稀释。**

```
非重叠窗口的问题（5分钟桶）：

  23:55        00:00        00:05        00:10
    │            │            │            │
  ──┼──桶A───────┼──桶B───────┼──桶C───────┼──
    │            │            │            │
       CPU突增: ██████████████
       (23:58 ~ 00:03，跨越桶A和桶B)

  桶A 只包含突增的前 2 分钟 → p99 轻微抬高，但不够显著
  桶B 只包含突增的后 2 分钟 → p99 轻微抬高，但也不够显著
  结果：一次持续 5 分钟的异常，在两个桶中都不够明显，被"平均掉了"
```

Trend 采用**重叠滑动窗口**：窗口大小 5 分钟，但每分钟滑动 1 分钟。相邻窗口之间有 4 分钟的重叠，每个原始数据点会参与连续 5 个窗口的分位值计算。

```
Trend 滑动窗口（5分钟窗口，1分钟步进）：

  23:55   23:56   23:57   23:58   23:59   00:00   00:01   00:02   00:03
    │       │       │       │       │       │       │       │       │
    └──W1───┘  (覆盖 23:51~23:56)
            └──W2───┘  (覆盖 23:52~23:57)
                    └──W3───┘  (覆盖 23:53~23:58)
                            └──W4───┘  (覆盖 23:54~23:59)
                                    └──W5───┘  (覆盖 23:55~00:00)
                                            └──W6───┘  (覆盖 23:56~00:01)
                                                    └──W7───┘  (覆盖 23:57~00:02)
                                                            └──W8───┘  (覆盖 23:58~00:03)

  同一次异常（23:58~00:03）：
    完整出现在 W8 中 → 异常在 p99 序列中形成连续的"隆起"，不会被稀释
```

重叠窗口的 p99 序列（异常事件 23:58~00:03）：

```
  00:01  00:02  00:03  00:04  00:05  00:06  00:07  00:08  00:09  00:10
  p99: 42 →  45 →  52 →  68 →  85 →  82 →  71 →  58 →  48 →  43
              ↑________ 异常隆起 _________↑

  大模型看到的模式：
    - 隆起从 00:02 开始（p99 开始偏离基线 42）
    - 00:06 达到峰值 85
    - 00:10 恢复正常 43
    - 持续约 8 分钟，峰值 85，严重程度：高
    - 形状：快速上升 → 短暂平台 → 快速下降 → 典型的突发型异常
```

**窗口大小可配置**：通过 `trend_cluster_task` 表中的 `slide_interval` 参数，不同场景可使用不同窗口大小：

- **高频指标**（CPU、内存）：3-5 分钟，保证快速响应
- **低频指标**（磁盘空间、备份状态）：10-15 分钟，样本本来就稀疏
- **容量规划指标**（存储空间增长率）：15-30 分钟，关注长期趋势而非短期波动

### 指标版本化：解耦代码与数据

Trend 采用**版本化指标属性**设计，将"计算哪些指标"与代码完全解耦，通过数据库配置驱动指标定义，使新增或调整指标无需修改代码和重新部署。

传统方案中，指标名称通常硬编码在数据模型、计算逻辑和查询接口中。当需要新增指标时，必须修改代码、更新表结构、重新部署。Trend 通过 `trend_cluster_task_version` 表定义每个任务类型的指标属性列表：

```json
// attributes: 版本化的指标属性定义
[
  {"name": "cpu_usage", "type": "float"},
  {"name": "dml",       "type": "int"},
  {"name": "qps",       "type": "float"}
]
```

分位值计算结果以紧凑的 JSON 数组存储在 `metrics_data` 字段中：

```json
// metrics_data: [[p99, p95, p90, p70, p50, p30, sample_count], ...]
// 外层数组索引 = attributes 中的顺序
[
  [78.5, 72.0, 68.0, 50.0, 35.0, 18.0, 120],  // cpu_usage (索引 0)
  [1000, 900, 800, 500, 300, 100, 5000],      // dml       (索引 1)
  [45.2, 42.1, 40.0, 30.0, 20.0, 10.0, 3000]  // qps       (索引 2)
]
```

查询时利用 MySQL 的 `JSON_EXTRACT` 函数在数据库层直接解析指定指标的分位值：

```sql
-- 查询 cpu_usage 的 p99（索引 [0][0]）
SELECT CAST(JSON_EXTRACT(metrics_data, '$[0][0]') AS DECIMAL) as value
FROM metric_features_03
WHERE cluster_name = 'prod' AND window_end >= '2026-01-01';

-- 一次查询多个分位值
SELECT
  CAST(JSON_EXTRACT(metrics_data, '$[0][0]') AS DECIMAL) as p99,
  CAST(JSON_EXTRACT(metrics_data, '$[0][4]') AS DECIMAL) as p50,
  CAST(JSON_EXTRACT(metrics_data, '$[0][5]') AS DECIMAL) as p30
FROM metric_features_03
WHERE cluster_name = 'prod';
```

| 优势 | 说明 |
|------|------|
| **零代码扩展** | 新增指标只需添加一条 `attributes` 配置，无需修改代码 |
| **向后兼容** | 历史数据自带版本号，读取时按对应版本的属性顺序解析 |
| **MySQL 算力利用** | 通过 `JSON_EXTRACT` 在数据库层按需解析，减少应用层内存占用 |
| **存储紧凑** | JSON 数组存储比每指标一列的扁平表节省大量列空间 |
| **集群隔离** | 每个集群独立管理自己的指标版本配置，互不干扰 |

### 与传统监控的本质区别：连续流 vs 离散采样

```
Zabbix/Prometheus 的工作方式：

  每 30s/60s 采集一次，取当前时刻的瞬时值

  00:00     00:30     01:00     01:30     02:00
    │         │         │         │         │
    ▼         ▼         ▼         ▼         ▼
   42%       38%       95%*      41%       39%

  问题：
    1. 两次采集之间的 30s/60s 内发生了什么，完全不可知
    2. 采集间隔本身就是盲区，间隔越长盲区越大
    3. 瞬时值受采样时刻影响大
    4. "趋势"只是离散点的连线，中间段是脑补出来的
```

```
Trend 的工作方式：

  原始数据：每秒从 ES 流入的连续数据流
  每分钟执行一次 5 分钟滑动窗口，计算 6 个分位值

  数据流（秒级，来自 ES）：
    00:00:01 → 42.1  00:00:02 → 41.8  00:00:03 → 43.2 ...
    每一秒都有记录，没有采样间隔，没有盲区

  滑动窗口（每分钟产出 1 个数据点 × 6 分位）：
    00:05 窗口 [00:00~00:05]: p99=78 p95=72 p50=35 ...
    00:06 窗口 [00:01~00:06]: p99=80 p95=74 p50=36 ...
    00:07 窗口 [00:02~00:07]: p99=82 p95=76 p50=35 ...

  关键区别：
    ✓ 不是"每 5 分钟采一个点"，而是"5 分钟内所有秒级数据全部参与计算"
    ✓ 窗口内 300 个原始数据点的完整分布被压缩为 6 个精确分位值
    ✓ 趋势曲线不是离散点连线，而是每个点背后都有 300 个样本的统计支撑
```

| 维度 | Zabbix/Prometheus | Trend |
|------|-------------------|-------|
| 数据来源 | Agent 每 30s/60s 轮询采集 | 秒级连续数据流（ES/Kafka） |
| 时间盲区 | 两次采集间隔内完全不可知 | 无盲区，所有数据点参与窗口计算 |
| 每个时间点的信息量 | 1 个瞬时值（或短窗口均值） | 6 个分位值，完整反映窗口内数据分布 |
| "趋势"的实质 | 离散采样点的连线 | 连续滑动窗口的分位值序列 |
| 异常检测能力 | 阈值告警，只能判断"当前是否超限" | 形态识别，能判断异常类型、严重程度、持续时间 |
| 大模型分析价值 | 低——信息量不足，只能做简单阈值判断 | 高——完整的趋势区间带 + 时间连续性 = 可推理的数据 |
| 数据压缩比 | 无压缩（原始采样值） | 300 个原始点 → 6 个分位值，信息密度 ×50 |

> **一句话总结**：传统监控是"每隔 N 秒拍一张照片"，Trend 是"5 分钟录像带的 6 帧关键画面"——前者丢失了照片之间的所有信息，后者保留了录像带中的完整趋势。

## 快速开始

### 1. 环境准备

- Go 1.25+
- MySQL（建库后表由 GORM AutoMigrate 自动创建）
- Elasticsearch v8
- Etcd

### 2. 编译

```bash
go build -o bin/trend-master ./cmd/master
go build -o bin/trend-worker ./cmd/worker
```

### 3. 配置

在 `configs/config.yaml` 中配置各组件连接参数：

```yaml
app:
  cluster_name: prod-cluster-1

etcd:
  endpoints:
    - http://10.10.10.30:2379
  prefix: trend

logger:
  level: info
  output: stdout  # 或文件路径

master:
  mysql:
    host: 10.10.10.40
    port: 3306
    dbname: trend_config
    user: root
    password: "..."
    max_idle_conns: 10
    max_open_conns: 100
    conn_max_lifetime: 1
  api_addr: :8080
  cron_expr: "*/1 * * * *"
  task_path: /tasks
  backlog_threshold: 100

worker:
  master_api: http://127.0.0.1:8080
  concurrency: 10
  metrics_addr: :9090
```

### 4. 初始化数据

```sql
-- 任务类型
INSERT INTO trend_cluster_task (cluster_name, task_name, status, slide_interval, stale_threshold_minutes) VALUES
('prod-cluster-1', 'orzdba', 1, 5, 30);

-- 指标版本配置（版本 1）
INSERT INTO trend_cluster_task_version (cluster_name, task_name, version, attributes, description) VALUES
('prod-cluster-1', 'orzdba', 1,
```

## 分表说明

分位值结果按 `calc_instance_id % 10` 哈希路由到 `metric_features_00` ~ `metric_features_09` 共 10 张分表。

- `calc_instance_id` 是 `trend_orzdba_calc_instance` 表的自增主键，在创建任务时由 Master 端传入
- 每张分表包含 `cluster_name`、`version` 和 `metrics_data`（JSON）字段
- 查询时通过 `cluster_name + calc_instance_id` 精确定位分表并过滤
- 详细表结构文档见 [docs/tables.md](docs/tables.md)

## 智能化应用场景

### 容量趋势预测

- 输入：某实例最近 12 小时的分钟级 CPU 全分位值（720 个点 × 6 分位）+ 过去 30 天的日级聚合趋势
- 分析：观察 p99 的 30 天走势，预估到达 90% 警戒线的时间
- 输出：风险等级 + 预计天数 + 建议措施（扩容/优化慢 SQL/调整业务时段）

### 趋势偏离预警

- 输入：异常时刻前后 4 小时的全指标分钟级数据 + 昨天/上周同时段对比
- 分析：识别偏移模式（突增/缓增/周期性偏移），关联多个指标
- 输出：异常解释报告，标注可能的业务原因

### 根因关联分析

- 输入：同一时段内多个指标的分钟级全分位值序列
- 分析：判断指标间的因果关系，识别连带效应
- 输出：根因排序和置信度

## 开发

- 添加新任务类型：在 `internal/task` 下实现 `Task` 接口，在 `internal/master/publisher.go` 的 `NewTaskPublisher` 中注册
- 新增指标：在 `trend_cluster_task_version` 表中添加或更新 `attributes` 配置，无需修改代码
- 提交前确保 `go build ./...` 和 `go test ./...` 均通过

---

> **Trend 不做分析，只做数据。**
>
> 它把原始监控数据从"噪声"变成"信号"——数百万条原始记录压缩为数千个精确的分位值数据点，这些分位值序列天然构成趋势区间带，是大模型进行容量分析、趋势预测、异常检测的最佳数据输入。
>
> 大模型的分析能力有多强，取决于它拿到的数据有多好。Trend 就是那个让数据"好到值得让大模型分析"的基础设施。
